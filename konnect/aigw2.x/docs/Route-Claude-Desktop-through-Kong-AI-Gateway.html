Kong AI Gateway

Route Claude Desktop through Kong AI Gateway

Point Claude Desktop at a Kong AI Gateway that serves Claude models by family (Opus, Sonnet, Haiku), authenticated with a static API key or with Microsoft Entra ID (OIDC). The gateway holds the real Anthropic credential; Claude Desktop only ever talks to the gateway.

Objective

What this gets you

Claude Desktop normally talks straight to Anthropic. Third-party inference redirects it to a gateway you run. Routed through Kong, you get one place for the Anthropic credential, version pinning per model family, usage visibility, and policy. This guide sets up two inbound credential kinds side by side: a Static API key (key-auth) and Entra ID bearer tokens (an openid-connect auth strategy). A request is accepted if it satisfies either one.

Claude Desktop only runs Claude models. A gateway changes where Claude inference is served and which provider serves it. It does not let Claude Desktop use Gemini, GPT, or any non-Claude family. The gateway target must be a Claude model served in Anthropic format.
Before you start

Prerequisites

Already in place
  • ✓ Control plane available. An AI Gateway 2.x control plane in Konnect.
  • ✓ Cluster certificates created. A data plane certificate registered with the AI Gateway for mTLS.
  • ✓ Data plane deployed. A data plane running and reachable.
Also required for Claude Desktop
  • □ kongctl on a recent version, with your Konnect token exported as KONNECT_TOKEN.
  • □ Gateway identity known: AI_GATEWAY_ID and the region URL KONNECT_CONTROL_PLANE_URL.
  • □ Anthropic API key (the sk-ant-... value) available in your shell as an environment variable.
  • □ Gateway adopted into a kongctl namespace.
  • □ Anthropic-format model on /v1/messages. Claude Desktop speaks the Anthropic Messages API, not the OpenAI format.
  • □ HTTPS with a trusted certificate on the data plane. Claude Desktop requires an HTTPS base URL and validates the certificate. A self-signed certificate is rejected unless its CA is trusted on the machine.
  • □ Egress and DNS from the data plane to api.anthropic.com. The data plane makes the upstream call.
  • □ Claude Desktop with third-party inference (a recent build, Developer mode available).
For Entra ID (OIDC) sign-in
  • □ Entra ID app registration for the gateway API, with permission to edit its manifest, expose an API, and create app roles (Step 5 walks through it).
  • □ Tenant ID, client ID, and a client secret for that registration.
  • □ Egress from the data plane to login.microsoftonline.com, so Kong can fetch Entra's discovery document and signing keys.
  • □ OpenAI API key if you also expose the OpenAI model for CLI tools (Step 5). Claude Desktop does not use it.
Production data plane

Deploy the data plane on a VM

The earlier prerequisite assumed a data plane already exists. For production on a VM there are two ways to run the AI Gateway 2.x data plane. Option A uses Kong's published OS package and is the path to prefer. Option B runs the published container image under Podman; it works and is what this environment uses today, but a manual container deployment of the 2.x data plane is not yet Kong-verified.

Option A: OS package (Kong-published, recommended)

Kong publishes the AI Gateway 2.x data plane as an OS package in the Cloudsmith ai-gateway-22 repository, in both a standard and a FIPS 140-3 build. The AI Gateway runs on the same OpenResty engine as the regular gateway, so the familiar package, hybrid kong.conf, and systemd pattern applies. The binary runs on the host, so there is no container DNS layer to work around.

shell (RHEL / EL 9)
# add the ai-gateway-22 repo (confirm the exact URL on the Cloudsmith page)
curl -1sLf 'https://packages.konghq.com/public/ai-gateway-22/setup.rpm.sh' | sudo bash

# standard build
sudo dnf install -y kong-ai-gateway
# or the FIPS 140-3 build:
# sudo dnf install -y kong-ai-gateway-fips-140-3

# Debian / Ubuntu equivalent:
# curl -1sLf 'https://packages.konghq.com/public/ai-gateway-22/setup.deb.sh' | sudo bash
# sudo apt install -y kong-ai-gateway

Place the data plane certificate (the one registered with your AI Gateway), configure the node as a hybrid data plane, and start it under systemd.

/etc/kong/kong.conf
role = data_plane
database = off
konnect_mode = on
cluster_mtls = pki
cluster_control_plane = <cp-endpoint>:443
cluster_server_name = <cp-endpoint>
cluster_telemetry_endpoint = <telemetry-endpoint>:443
cluster_telemetry_server_name = <telemetry-endpoint>
cluster_cert = /etc/kong/certs/tls.crt
cluster_cert_key = /etc/kong/certs/tls.key
lua_ssl_trusted_certificate = system
proxy_listen = 0.0.0.0:8000, 0.0.0.0:8443 ssl
shell
sudo mkdir -p /etc/kong/certs
sudo install -m 0600 tls.crt tls.key /etc/kong/certs/

# start, then manage with systemd (Kong ships systemd integration)
sudo kong start -c /etc/kong/kong.conf
sudo systemctl enable --now kong    # if using the packaged unit

The node should show Connected and Compatible under your AI Gateway in Konnect. Because the binary runs on the host, DNS comes straight from the host's /etc/resolv.conf, so the container resolver mismatch does not apply here.

Data plane version, Konnect-managed. With a Konnect control plane, data planes run across a supported version range rather than an exact match. Kong recommends one major version of data plane per control plane; if versions are mixed, the control plane serves the least common subset of configuration across the connected data planes. Keep the data planes on a current, supported AI Gateway 2.2.x build and upgrade them together; you do not need to match the control plane patch for patch.

Option B: Podman container (viable, not yet Kong-verified)

Running the published kong/kong-ai-gateway container under Podman works and is what this environment uses today. A manual container deployment of the AI Gateway 2.x data plane is not a Kong-verified production path, so prefer Option A, or confirm this configuration with the Kong AI Gateway team before go-live. For production, supervise the container with systemd through a Quadlet unit rather than a bare run.

shell (container)
podman run -d --name kong-dp --restart always \
  --dns <internal-dns-1> --dns <internal-dns-2> \
  -e KONG_ROLE=data_plane \
  -e KONG_DATABASE=off \
  -e KONG_KONNECT_MODE=on \
  -e KONG_CLUSTER_MTLS=pki \
  -e KONG_CLUSTER_CONTROL_PLANE=<cp-endpoint>:443 \
  -e KONG_CLUSTER_SERVER_NAME=<cp-endpoint> \
  -e KONG_CLUSTER_TELEMETRY_ENDPOINT=<telemetry-endpoint>:443 \
  -e KONG_CLUSTER_TELEMETRY_SERVER_NAME=<telemetry-endpoint> \
  -e KONG_CLUSTER_CERT=/etc/secrets/kong-cluster-cert/tls.crt \
  -e KONG_CLUSTER_CERT_KEY=/etc/secrets/kong-cluster-cert/tls.key \
  -e KONG_LUA_SSL_TRUSTED_CERTIFICATE=system \
  -v /etc/kong/certs/tls.crt:/etc/secrets/kong-cluster-cert/tls.crt:ro,Z \
  -v /etc/kong/certs/tls.key:/etc/secrets/kong-cluster-cert/tls.key:ro,Z \
  -p 8000:8000 -p 8443:8443 \
  docker.io/kong/kong-ai-gateway:2.2.0
Container DNS caveat. Podman does not always inherit the host's resolvers; it can inject its own stub resolver as the first nameserver, which caused the "name resolution failed" upstream errors. Passing --dns with your internal resolvers (above) is the fix. Option A avoids this entirely by running on the host network stack. For production supervision, convert this run into a Quadlet .container unit under /etc/containers/systemd/ so systemd manages restarts and boot start, or set a host-wide default with dns_servers in /etc/containers/containers.conf.

Provider, family models, key-auth, consumer

The provider holds the Anthropic key and sends it outbound as x-api-key (Anthropic's header). Each model is Anthropic format, serving the Messages API, and represents one family: clients send the family alias (claude-opus, claude-sonnet, claude-haiku) in the model field, and the target pins the exact upstream version. Sending the upstream version id directly is rejected, so only pinned versions are reachable. The key-auth strategy gates inbound requests; the consumer holds the key Claude Desktop sends.

ai-gateway-kongctl.yaml
_defaults:
  kongctl:
    namespace: ai-gateway-kongctl

ai_gateway_model_providers:
- ref: anthropic-provider
  ai_gateway: !lookup {id: !env 'AI_GATEWAY_ID'}
  name: anthropic-provider
  display_name: Anthropic
  type: anthropic
  config:
    auth:
      type: basic
      headers:
      - name: x-api-key
        value: !secret {source: !env 'ANTHROPIC_API_KEY'}

ai_gateway_auth_strategies:
- ref: claude-key-auth
  ai_gateway: !lookup {id: !env 'AI_GATEWAY_ID'}
  name: claude-key-auth
  display_name: Claude Key Auth
  type: key-auth
  config:
    key_names: [x-api-key]
    hide_credentials: true

ai_gateway_consumers:
- ref: claude-desktop
  ai_gateway: !lookup {id: !env 'AI_GATEWAY_ID'}
  name: claude-desktop

Keep every model in this file. A model created in the Konnect UI is saved with UI defaults: no auth strategy (access: {}), max_request_body_size: 0, and a balancer with 5 retries. An Opus model created that way accepted unauthenticated requests. Manage all models declaratively so they share one auth configuration, and compare with kongctl get ai-gateway models <name> --gateway-name <gw> -o yaml. Use apply, not sync, while resources outside this file exist on the gateway; sync deletes them.
Upgrading a family. To move Opus to a newer version, change only targets[].name and apply again. Clients keep sending claude-opus.
4

Test from the command line

Claude Desktop will call /v1/messages. Confirm the gateway answers with the key before wiring the app.

shell
export AIGW_HTTPS='https://your.gateway.host'   # trusted-cert host, not an IP

curl -s -i "$AIGW_HTTPS/v1/messages" \
  -H "Content-Type: application/json" \
  -H "anthropic-version: 2023-06-01" \
  -H "x-api-key: ${CONSUMER_API_KEY}" \
  -d '{"model":"claude-sonnet","max_tokens":64,"messages":[{"role":"user","content":"ping"}]}'

# every family must reject a request without a credential
for m in claude-opus claude-sonnet claude-haiku; do
  curl -s -o /dev/null -w "$m %{http_code}\n" "$AIGW_HTTPS/v1/messages" \
    -H "Content-Type: application/json" -H "anthropic-version: 2023-06-01" \
    -d "{\"model\":\"$m\",\"max_tokens\":8,\"messages\":[{\"role\":\"user\",\"content\":\"ping\"}]}"
done    # expect 401 for all three

A 200 with a completion means the full path works: inbound key-auth, Anthropic-format routing, outbound Anthropic credential. The loop must print 401 for every family; a 200 there means that model has no auth strategy. If curl needs --insecure to pass, the certificate is not trusted, fix that before Claude Desktop, which will not skip certificate validation.

5

Add Entra ID sign-in (OIDC auth strategy)

An openid-connect auth strategy lets callers present an Entra ID access token as Authorization: Bearer instead of a static key. Kong validates the token signature against Entra's published keys, checks the issuer, audience, and expiry, then maps the token to an AI Consumer. The strategy is added next to key-auth, so existing key users keep working.

5a. Register the gateway API in Entra ID

  • 1 App registrations, New registration: name it, for example, kong-ai-gateway-api, single tenant. Copy the Application (client) ID into CLIENT_ID and the Directory (tenant) ID into TENANT_ID.
  • 2 Expose an API: set the Application ID URI to api://<CLIENT_ID>.
  • 3 Manifest: set requestedAccessTokenVersion (shown as accessTokenAcceptedVersion in the legacy manifest view) to 2. Without this Entra issues v1 tokens with issuer https://sts.windows.net/<tenant>/, which does not match ISSUER_URL, and every request is rejected with 401.
  • 4 Certificates & secrets: create a client secret and copy its value into CLIENT_SECRET.
  • 5 Optional, recommended: App roles. Create a role such as AIGateway.Access (allowed member types: Users/Groups and Applications). Assign it to the users and applications allowed to call the gateway, so you can require it at the gateway (see the commented lines below).

5b. Auth strategy, consumer, and models

This file creates the strategy, an AI Consumer for a CLI tool that authenticates with client credentials, and an OpenAI model for OpenAI-format CLI tools, and attaches the strategy to every model. Claude Desktop only uses the Claude models; the OpenAI model is for other clients on the same gateway.

entra-oidc-kongctl.yaml
_defaults:
  kongctl:
    namespace: ai-gateway-kongctl

ai_gateway_auth_strategies:
- ref: identity-oidc
  ai_gateway: !lookup {id: !env 'AI_GATEWAY_ID'}
  display_name: "Identity OIDC (Entra ID)"
  name: identity-oidc
  type: openid-connect
  config:
    issuer: !env 'ISSUER_URL'        # https://login.microsoftonline.com/<tenant-id>/v2.0
    client_id:
    - !env 'CLIENT_ID'               # gateway API app registration
    client_secret:
    - !secret {source: !env 'CLIENT_SECRET'}
    auth_methods:
    - bearer                         # validate tokens the caller already has
    scopes:
    - !env 'ENTRA_SCOPE'             # api://<CLIENT_ID>/.default; only used when Kong itself requests tokens
    audience_required:
    - !env 'CLIENT_ID'               # v2 tokens carry the API app's client ID in "aud"
    consumer_claims:
    - - azp                          # v2 token: client ID of the calling application
    consumer_by:
    - custom_id                      # match "azp" against the AI Consumer's custom_id
    # Claude Desktop users (interactive sign-in) do not map to an AI Consumer;
    # allow valid user tokens through and gate them by app role instead:
    # consumer_optional: true
    # roles_claim: [roles]
    # roles_required: [AIGateway.Access]
    cache_tokens_salt: identity-oidc-cache-salt

ai_gateway_consumers:
- ref: cli-tool-consumer
  ai_gateway: !lookup {id: !env 'AI_GATEWAY_ID'}
  display_name: "CLI Tool Consumer"
  name: cli-tool-consumer
  type: oauth
  custom_id: !env 'CLIENT_ID'        # equals "azp" in the CLI tool's tokens
  policies: []

ai_gateway_model_providers:
- ref: generic-openai
  ai_gateway: !lookup {id: !env 'AI_GATEWAY_ID'}
  name: generic-openai
  display_name: "generic-openai"
  type: openai
  config:
    auth:
      type: basic
      headers:
      - name: Authorization
        value: !secret {source: !env 'OPENAI_AUTH_HEADER'}

ai_gateway_models:
- ref: my-gpt-4o-mini
  ai_gateway: !lookup {id: !env 'AI_GATEWAY_ID'}
  display_name: my-gpt-4o-mini
  name: my-gpt-4o-mini
  type: model
  enabled: true
  formats: [{type: openai}]
  access:
    auth_strategies:
    - !ref identity-oidc#name
  config:
    route:
      paths: [/]
      model:
        body_param: model
        values: [my-gpt-4o-mini]
  capabilities: [generate]
  targets:
  - name: gpt-4o-mini
    provider: generic-openai
    config:
      type: openai

Then attach the same strategy to the Claude models in ai-gateway-kongctl.yaml from Step 3, next to key-auth, on all three families:

ai-gateway-kongctl.yaml (each claude-* model)
  access:
    auth_strategies:
    - claude-key-auth
    - identity-oidc                  # accepted if either strategy passes

Why the config differs from the generic OIDC example

consumer_claims: azp (not sub)In Entra ID client-credentials tokens, sub is the service principal's object ID, not the client ID. The consumer's custom_id is the client ID, which Entra puts in azp (v2 tokens; v1 tokens use appid). Mapping sub to a custom_id of CLIENT_ID never matches, and every request ends in 401.
audience_requiredRestricts accepted tokens to ones issued for this API. Any token from your tenant would otherwise pass signature and issuer checks.
scopesEntra scopes take the form api://<client-id>/<scope>; /.default requests all granted permissions. With auth_methods: [bearer] this value is not checked on incoming tokens. To enforce a delegated scope use scopes_claim: [scp] with scopes_required; client-credentials tokens carry roles, not scp.
One OIDC strategy per gatewayAll AI Models in an AI Gateway that use OIDC must reference the same openid-connect strategy, so identity-oidc serves both the CLI tool and Claude Desktop users. That is why user-token handling (consumer_optional, roles) is configured on the same strategy.
AuthorizationAuthentication only proves who is calling. Every holder of a valid token for this API passes on every model that references the strategy. Use access.acls on a model, or the app-role check above, to limit who reaches which model.
6

Test Entra ID tokens

Get a client-credentials token for the gateway API, check its claims, then call both a Claude model and the OpenAI model with it.

shell
TOKEN=$(curl -s -X POST "https://login.microsoftonline.com/${TENANT_ID}/oauth2/v2.0/token" \
  -d grant_type=client_credentials \
  -d client_id="${CLIENT_ID}" \
  --data-urlencode client_secret="${CLIENT_SECRET}" \
  --data-urlencode scope="${ENTRA_SCOPE}" | jq -r .access_token)

# check claims: iss must equal ISSUER_URL, aud must equal CLIENT_ID, azp must equal CLIENT_ID
echo "$TOKEN" | cut -d. -f2 | tr '_-' '/+' | base64 -d 2>/dev/null | jq '{iss, aud, azp, appid, roles, ver}'

# Claude model with the Entra token
curl -s -i "$AIGW_HTTPS/v1/messages" \
  -H "Content-Type: application/json" \
  -H "anthropic-version: 2023-06-01" \
  -H "Authorization: Bearer ${TOKEN}" \
  -d '{"model":"claude-sonnet","max_tokens":64,"messages":[{"role":"user","content":"ping"}]}'

# OpenAI model (base path "/", so the endpoint is /chat/completions)
curl -s -i "$AIGW_HTTPS/chat/completions" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer ${TOKEN}" \
  -d '{"model":"my-gpt-4o-mini","messages":[{"role":"user","content":"ping"}]}'
200Token validated and mapped to cli-tool-consumer; requests appear under that consumer in Konnect.
401, iss is sts.windows.netThe API app still issues v1 tokens. Set requestedAccessTokenVersion to 2 (Step 5a) and request a new token.
401, aud is not CLIENT_IDThe token was requested for another resource. Request it with scope=api://<CLIENT_ID>/.default.
401, claims look rightNo AI Consumer matched. Check that azp equals the consumer's custom_id, or set consumer_optional: true for callers that should not map to a consumer.
One app or two. This guide uses the gateway API registration as its own client for brevity, so CLIENT_ID appears as the audience and as azp. In production, register each CLI tool or service as a separate client app, grant it the API's app role, and set the consumer's custom_id to that client's ID.

Model discovery

GET /v1/models, built from the configured models

Claude Desktop calls GET /v1/models to test the connection and fill its model picker. AI Models only serve inference paths, so nothing on the gateway answers that request by default. The pattern below hosts it on a passthrough-listener AI MCP Server at /v1/models with a pre-function policy that answers the request itself; the upstream URL is never contacted.

The list is not hardcoded. On each request (cached for 30 seconds per worker) the function reads the gateway's AI Models from the Konnect API and returns every enabled Anthropic-format model that has an alias. Add, disable, or rename a Claude family model and /v1/models follows within 30 seconds, with no redeploy. The gateway ID and Konnect region are derived from the data plane's own cluster_control_plane setting, so the same policy works on any gateway.

Requirements
  • □ untrusted_lua = lax on every data plane (KONG_UNTRUSTED_LUA=lax). The default strict sandbox blocks the HTTP call and the vault lookup. lax applies to every pre- and post-function on the data plane, so restrict who can create those policies.
  • □ A read-only Konnect token (system account) that can list AI Gateways and read their models. Day 1: paste it into KONNECT_TOKEN in the Lua; it is visible to anyone who can read policies. Day 2: store it in a secret manager behind an AI Vault and set KONNECT_TOKEN = "{vault://gcp-sm/konnect-models-pat}".
  • □ Egress from the data plane to <region>.api.konghq.com.
v1-models-kongctl.yaml
_defaults:
  kongctl:
    namespace: ai-gateway-kongctl
ai_gateway_policies:
- ref: models-list-pre-function
  ai_gateway: !lookup {id: !env 'AI_GATEWAY_ID'}
  name: models-list-pre-function
  display_name: Models List Pre-function
  type: pre-function
  enabled: true
  global: false
  config:
    access:
    - |
      local http  = require("resty.http")
      local cjson = require("cjson.safe")

      local KONNECT_TOKEN = "<read-only-konnect-token>"
      local GATEWAY_ID    = nil   -- optional override; nil = discover at runtime

      local CACHE_TTL   = 30
      local RETRY_AFTER = 5
      local JSON        = { ["Content-Type"] = "application/json" }

      -- "9146d23eb2.us.cp.konghq.com:443" -> host, region "us"
      local cp_host = tostring(kong.configuration.cluster_control_plane or ""):match("^([^:/]+)")
      local region  = cp_host and cp_host:match("^[^.]+%.([^.]+)%.cp%.konghq%.com$")
      local KONNECT_API = "https://" .. (region or "us") .. ".api.konghq.com"

      local cache = { body = nil, expires = 0 }

      local function get_token()
        if KONNECT_TOKEN:sub(1, 9) == "{vault://" then
          local value, err = kong.vault.get(KONNECT_TOKEN)
          if not value then return nil, "vault lookup failed: " .. tostring(err) end
          return value
        end
        return KONNECT_TOKEN
      end

      local function konnect_get(path, token)
        local httpc = http.new()
        httpc:set_timeout(3000)
        local res, err = httpc:request_uri(KONNECT_API .. path, {
          method  = "GET",
          headers = { ["Authorization"] = "Bearer " .. token, ["Accept"] = "application/json" },
          ssl_verify = true,
        })
        if not res then return nil, path .. " request failed: " .. tostring(err) end
        if res.status ~= 200 then return nil, path .. " returned " .. res.status end
        local doc = cjson.decode(res.body)
        if type(doc) ~= "table" then return nil, path .. " returned invalid JSON" end
        return doc
      end

      -- Finds the AI Gateway whose definition mentions this data plane's control
      -- plane host (or its cluster prefix). Resolved once per worker, then reused.
      local function resolve_gateway_id(token)
        if GATEWAY_ID then return GATEWAY_ID end
        if not cp_host or cp_host == "" then
          return nil, "cluster_control_plane is not set on this data plane"
        end
        local doc, err = konnect_get("/v1/ai-gateways?page%5Bsize%5D=100", token)
        if not doc then return nil, err end

        local prefix = cp_host:match("^([^.]+)")
        for _, gw in ipairs(doc.data or doc) do
          local raw = cjson.encode(gw) or ""
          if raw:find(cp_host, 1, true) or (prefix and raw:find(prefix, 1, true)) then
            GATEWAY_ID = gw.id
            kong.log.notice("[models-list] resolved AI Gateway ", gw.name or "?", " (", gw.id, ")")
            return GATEWAY_ID
          end
        end
        return nil, "no AI Gateway visible to the token matches " .. cp_host
      end

      local function has_format(model, wanted)
        for _, f in ipairs(model.formats or {}) do
          if type(f) == "table" and f.type == wanted then return true end
        end
        return false
      end

      local function fetch_models()
        local token, terr = get_token()
        if not token then return nil, terr end
        local gateway_id, gerr = resolve_gateway_id(token)
        if not gateway_id then return nil, gerr end

        local doc, err = konnect_get("/v1/ai-gateways/" .. gateway_id .. "/models?page%5Bsize%5D=100", token)
        if not doc then return nil, err end

        local list = {}
        for _, m in ipairs(doc.data or doc) do
          local alias = type(m.config) == "table" and type(m.config.route) == "table"
            and type(m.config.route.model) == "table" and type(m.config.route.model.values) == "table"
            and m.config.route.model.values[1]
          if m.enabled ~= false and has_format(m, "anthropic") and type(alias) == "string" and alias ~= "" then
            list[#list + 1] = {
              type = "model",
              id = alias,
              display_name = m.display_name or m.name,
              created_at = m.created_at,
            }
          end
        end
        table.sort(list, function(a, b) return a.id < b.id end)

        if #list == 0 then
          return '{"data":[],"has_more":false,"first_id":null,"last_id":null}'
        end
        return cjson.encode({
          data = list,
          has_more = false,
          first_id = list[1].id,
          last_id = list[#list].id,
        })
      end

      return function()
        if kong.request.get_method() ~= "GET" then
          return kong.response.exit(405, '{"error":"method not allowed"}', JSON)
        end

        local now = ngx.now()
        if not cache.body or now >= cache.expires then
          local body, err = fetch_models()
          if body then
            cache.body, cache.expires = body, now + CACHE_TTL
          elseif cache.body then
            kong.log.warn("[models-list] refresh failed, serving cached list: ", err)
            cache.expires = now + RETRY_AFTER
          else
            kong.log.err("[models-list] ", err)
            return kong.response.exit(503, '{"error":"model list unavailable"}', JSON)
          end
        end

        return kong.response.exit(200, cache.body, JSON)
      end

Check gateway discovery first. The function finds its AI Gateway by searching the gateway objects for the data plane's control plane host. Confirm the host appears with kongctl get ai-gateways -o json | grep -c <cp-prefix> (for example 9146d23eb2). If it returns 0, set GATEWAY_ID in the Lua as an override. Errors are logged on the data plane with the prefix [models-list].
One auth strategy per MCP server. An AI MCP Server accepts a single auth strategy, unlike a model. Claude Desktop sends the same credential on /v1/models as on inference, so attach the strategy that matches its credential kind: claude-key-auth for the static key, identity-oidc for Entra ID sign-in. Authentication runs before policies, so the list is never served to an unauthenticated caller.
Naming. Policy names cannot contain a slash, so the policy is models-list-pre-function; the endpoint path comes from route.paths. Keep only one entity on /v1/models. Remove any earlier static or request-termination version before applying this one.
